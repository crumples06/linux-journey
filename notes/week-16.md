## SSH
SSH lets you open a shell on another machine over an encrypted connection. There are two programs: the client (ssh, on your PC) and the server (sshd, running in each container, listening on port 22). Everything after the handshake is encrypted, so someone watching the network sees only noise.

- "Is this really the server I meant to reach?" This is answered with the server's host keys.
- "Are you allowed in?" This is answered with your user key.

Each sshd has its own key pair in `/etc/ssh/ssh_host_*`. On your first connection, the server presents its public host key and your client shows you the fingerprint (the "authenticity of host can't be established" prompt). If you say yes, the client stores it in `~/.ssh/known_hosts`, under an entry like `[localhost]:2222`. On every later connection it compares. If the key doesn't match, you get the big "REMOTE HOST IDENTIFICATION HAS CHANGED" warning, because a changed key is what a man-in-the-middle attack would look like.

All this learning about ssh in depth started because i started a new project 'Bastion access project'. Firstly i wanted to setup a bastion that will act as a middleman between outside and the servers inside the network. This meant that i cant allow any outside connections directly to the servers. I had to set up a ssh connection between the host and the bastion and also for the servers. 

I made a pair with ssh-keygen:
- The private key stays on the PC. A passphrase encrypts this file on disk, so a stolen copy is useless without it.
- The public key can be shared. It went into `/home/admin/.ssh/authorized_keys` in each container, which is sshd's list of "keys allowed to log in as admin."

When I connect, sshd sends a challenge. My client signs it with the private key, and sshd checks the signature against the public key in authorized_keys. The private key never travels over the network, only the signature does.

I can't connect straight to server1, so my client does two things:
- It opens SSH connection #1 to the bastion (`localhost:2222`) and authenticates.
- Through that connection it asks the bastion to forward traffic to `server1:22`. The bastion just relays the bytes.
- Inside that relayed path, my PC opens SSH connection #2, directly with server1, and authenticates again.

Connection #2 is encrypted end to end between my PC and server1, so the bastion only relays encrypted bytes and can't read the session. That's also why the private key never needs to be on the bastion. My PC answers both authentication challenges.

Connection #1 is started by a separate ssh process that my command launches behind the scenes. That process doesn't receive the `-i keys/key` option, and `-i` only applies to the final destination. So for the bastion it found no key. It looked in the default places (`~/.ssh/id_*` and an ssh-agent), found nothing, and fell back to the last method sshd offered, which was a password. admin has no password, so that could never work.

Fix for this:
A config file (ssh_config) tells ssh which key and settings to use for each host name, so it doesn't rely on defaults. ProxyJump bastion inside it sets up the jump.
```
Host bastion
    HostName localhost
    Port 2222
    User admin
    IdentityFile keys/key

Host server1 server2
    User admin
    ProxyJump bastion
    IdentityFile keys/key
```

## Bastion Project
A bastion (jump host) is a single, hardened entry point that sits between the outside world and a set of private machines. Nothing reaches the private machines except through it.

To make the servers truly private i had to make 2 networks in docker, a public network and a private network. The bastion exists in both networks while the servers are only in the private network.

Host keys are generated by the `openssh-server` package at install time, not by a command i wrote. Since all three containers came from one image, they'd have shared the same host keys — a real problem, since host keys are supposed to be a machine's unique identity. Fix: delete them in the same `RUN` as the install (so they never persist in an image layer), and regenerate them at container start via an entrypoint script running `ssh-keygen -A`, followed by `exec sshd -D`.

`exec` matters for signal handling. Without it, the script (not `sshd`) stays `PID 1`, so docker stop doesn't reach `sshd` directly and Docker has to wait out a timeout before killing it.

`sshd_config` vs `sshd_config.d/`: rather than editing the main config directly, I used the `Include` mechanism to drop a `hardening.conf` in with `PasswordAuthentication no` and `PermitRootLogin no`. Cleaner and less error-prone than appending to or sed-ing the original file. `sshd -T` shows the fully resolved config regardless of which file set what — the most trustworthy way to check a setting actually took effect.

## CA certificate
I wanted to add a ca service in the application, this would allow clients to connect to the servers through bastion using CA certified keys.

I first added a `ca` service in docker compose, it runs the official `smallstep/step-ca` image. It sits in it's own `ca` network since the servers and the bastion don't need to connect with it. It is isolated from the `public` and the `private` networks. It's API port is published at `127.0.0.1:9000` only. Its state lives in the `ca_data` named volume, so the ca keeps it identity across container restarts. 
Initializing this container involved some environment variables. The important one was `DOCKER_STEPCA_INIT_SSH: "true"` in particular, it makes the image initialize itself on the first start, creating 2 SSH signing keys: one for user certs and one for host certs.

The main idea is that, the user's public key will be signed by the CA, and the servers are configured to accept requests from the clients whose keys are signed (approved) by the CA. Similarly, the server's public key is also signed by the CA, which tells the client that the server they are connecting to is the right server trusted by the CA. 

I copied the public key into the `ca` container and then signed it using the command `step ssh certificate --sign --provisioner admin --principal admin --not-after 1h tanish /tmp/key.pub` this command then prompts a password that can be found in the `ca` container's logs using `docker logs ca`. This signed was then put back where the original public key was copied from.
I then exported the CA's public user key in the host machine as `user_ca.pub` to copy it into the image in `/etc/ssh/user_ca.pub` in dockerfile, and then added `TrustedUserCAKeys /etc/ssh/user_ca.pub` to `hardening.conf`. Added `CertificateFile keys/key-cert.pub` in both blocks (bastion and server1 server2) in ssh_config because `ProxyJump` opens two separate connections.

I then removed the `authorized_keys` part from dockerfile and recreated the containers. `/home/admin/.ssh` no longer exists on any host, and login still works. The CA's signature is now the only way in.

### Host Certs
The users certs are done and work properly and now the host certs are remaining. 
I first exported CA's host public key and build a project-local `known_hosts`:
```
docker cp ca:/home/step/certs/ssh_host_ca_key.pub ca/host_ca.pub
echo "@cert-authority [localhost]:2222,bastion,server1,server2 $(cat ca/host_ca.pub)" > ca/known_hosts
```

The [localhost]:2222 form is how OpenSSH writes a host with a non-standard port. My ssh_config connects to the bastion that way, so the pattern has to match it. The other names cover the jump hops.

Then added a block to the end of ssh_config:
```
Host *
    UserKnownHostsFile ca/known_hosts
    StrictHostKeyChecking yes
```
`Host *` applies to the hidden first-hop connection too (the same reason `CertificateFile` needed to be in both blocks). `StrictHostKeyChecking yes` means the client refuses any host it can't verify, with no prompt to accept. Using a separate file also keeps the global `~/.ssh/known_hosts` out of the test.

Host keys live on the named volumes, so we copy the public halves out:
```
mkdir -p ca/tmp
docker cp bastion:/etc/ssh/host_keys/ssh_host_ed25519_key.pub ca/tmp/bastion_host.pub
docker cp server1:/etc/ssh/host_keys/ssh_host_ed25519_key.pub ca/tmp/server1_host.pub
docker cp server2:/etc/ssh/host_keys/ssh_host_ed25519_key.pub ca/tmp/server2_host.pub
docker cp ca/tmp ca:/tmp/hostkeys
```

Then from inside the `ca` container:
```
cd /tmp/hostkeys
step ssh certificate --sign --host --provisioner admin --principal bastion --principal localhost --not-after 720h  bastion bastion_host.pub
step ssh certificate --sign --host --provisioner admin --principal server1 --not-after 720h server1 server1_host.pub
step ssh certificate --sign --host --provisioner admin --principal server2 --not-after 720h server2 server2_host.pub
```

The provisioner password is the one from `docker logs ca`. The bastion cert needs the extra localhost principal because my client connects to it by that name, and the client checks the name I typed against the cert's principals. 

Now, Bringing the certs back out, then into each container's volume:
```
docker cp ca:/tmp/hostkeys/. ca/tmp/
docker cp ca/tmp/bastion_host-cert.pub bastion:/etc/ssh/host_keys/ssh_host_ed25519_key-cert.pub
docker cp ca/tmp/server1_host-cert.pub server1:/etc/ssh/host_keys/ssh_host_ed25519_key-cert.pub
docker cp ca/tmp/server2_host-cert.pub server2:/etc/ssh/host_keys/ssh_host_ed25519_key-cert.pub
```

Add one line to hardening.conf:
```
HostCertificate /etc/ssh/host_keys/ssh_host_ed25519_key-cert.pub
```

Done, now certificates from both sides are implemeted.
