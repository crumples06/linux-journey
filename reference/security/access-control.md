# Access Control

Securing remote access, SSH-focused. Certificate-based login is in `ssh-ca.md`. Projects: `projects/ansible-devops-infra.md` (hardening role), `projects/bastion-ssh-ca.md`.

## How SSH works (the two questions)

SSH opens a shell on another machine over an encrypted connection. Two programs: the client (`ssh`) and the server (`sshd`, port 22 by default). After the handshake everything is encrypted.

| Question | Answered by |
|---|---|
| "Is this really the server I meant to reach?" | The server's **host keys** |
| "Are you allowed in?" | My **user key** |

### Host keys and `known_hosts`
- Each sshd has its own host key pair in `/etc/ssh/ssh_host_*`.
- On first connect the server presents its public host key and the client shows the fingerprint ("authenticity of host can't be established"). Saying yes stores it in `~/.ssh/known_hosts` (non-standard ports appear as `[localhost]:2222`).
- On later connections the client compares. A mismatch gives the big **"REMOTE HOST IDENTIFICATION HAS CHANGED"** warning, because a changed key is what a man-in-the-middle looks like.
- Host keys are generated by the `openssh-server` package at install time, so containers from one image share them unless regenerated at start (`dockerfile.md`).

### User keys
- `ssh-keygen` makes a pair. The **private key stays on my machine** (protect it with a passphrase). The **public key** goes in `~/.ssh/authorized_keys` of the target user.
- Login: sshd sends a challenge, my client signs it with the private key, sshd verifies against the public key. The private key never crosses the network, only the signature.

## Bastion / jump host

A bastion is a single hardened entry point between the outside world and private machines. Nothing reaches the private machines except through it.

```
Host bastion
    HostName localhost
    Port 2222
    User admin
    IdentityFile keys/key

Host server1 server2
    User admin
    ProxyJump bastion
    IdentityFile keys/key
```
How it works:
1. SSH connection #1: client to bastion, authenticated.
2. Through it, the bastion relays bytes to `server1:22`.
3. SSH connection #2, **inside** that relayed path, directly between my PC and server1, authenticated again.
- Connection #2 is end-to-end encrypted, so the bastion only relays ciphertext and cannot read the session. The private key never needs to be on the bastion.
- **Gotcha:** connection #1 is a separate hidden `ssh` process that does **not** receive `-i` from the command line. It looks in default places, finds nothing, and falls back to password. Put keys, certificates and known-hosts settings in `ssh_config`, in every relevant host block.
- Network design: bastion in both `public` and `private` networks, servers only in `private`.

## Hardening sshd

Use a drop-in instead of editing the main config:
```
# /etc/ssh/sshd_config.d/hardening.conf  (pulled in by Include)
PasswordAuthentication no
PermitRootLogin no            # or prohibit-password
```
- Verify what is *actually* in effect with `sshd -T`, which shows the fully resolved config regardless of which file set what.
- Edit the right file: `ssh_config` is the **client** config, `sshd_config` is the **server** config. Editing the wrong one succeeds silently.
- `PermitRootLogin without-password` is deprecated; modern OpenSSH wants `prohibit-password`. An unsupported option makes the reload fail, so test the config first (`sshd -t`).
- Apply with **reload**, never restart, when sshd is PID 1 in a container (restart kills the container).

### Lockout-safe ordering
Anything that can lock me out follows: **deploy -> verify -> disable**, never disable-then-hope.
1. Deploy the public key (Ansible `authorized_key`).
2. Prove key login works manually.
3. Only then disable password authentication.
After `docker compose down && up`, fresh containers have no key deployed. With the password fallback already removed that is a total lockout (`Permission denied (publickey,password)`). Keep a documented password-authenticated bootstrap run for fresh containers.

### Private key permissions
SSH refuses a private key that is group/world readable and silently falls back to password, which looks like a different bug. A bind mount can land the file as `0777`. Add a task that sets `0600` before any key-based connection, so it self-heals.

## Tradeoffs worth remembering

- **Passwordless sudo (`NOPASSWD:ALL`)**: needed because Ansible modules generally don't work under narrow sudo rules. Mitigated by making the account reachable only via key or short-lived certificate. Scoped sudo was considered and deferred.
- **Non-standard port (e.g. Termux's 8022)** is only a mild deterrent, not security.
- **Firewalling inside containers** isn't practical (see `firewall.md`); do it at the host/cloud layer.
